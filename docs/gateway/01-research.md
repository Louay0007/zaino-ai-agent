## a) Desktop login against a web portal

**Standard: Authorization Code + PKCE via system browser, never embedded webview.**
- RFC 7636 PKCE (`S256`, verifier 43–128 chars) — https://www.rfc-editor.org/info/rfc7636/ (2015) `[OLD but current]`. VERIFIED.
- RFC 8252 OAuth 2.0 for Native Apps (BCP 212) — public clients MUST use external user-agent + PKCE — https://www.rfc-editor.org/info/rfc8252/ (Oct 2017) `[OLD but current, still normative]`. VERIFIED.
- RFC 9700 OAuth Security BCP (Jan 2025) — PKCE required for ALL code flows, `S256` only, exact redirect-URI match (only exception: variable port on loopback), no Implicit grant, refresh-token rotation or sender-constraining for public clients — https://www.rfc-editor.org/info/rfc9700/ (2025-01-30). VERIFIED.

**Redirect choice for desktop: loopback first.** RFC 8252 §7: loopback `http://127.0.0.1:{ephemeral-port}/{path}` (IP literal, NOT `localhost` — proxy/firewall/hosts quirks), private-use scheme as fallback/foregrounding, claimed-HTTPS overkill for pure desktop. Tauri pieces VERIFIED current: `@tauri-apps/plugin-opener` `openUrl` (docs updated 2025-12-10); `@tauri-apps/plugin-deep-link` (updated 2026-06-15) + `@tauri-apps/plugin-single-instance` (updated 2026-08-28, required on Win/Linux so the second instance forwards the URL instead of just exiting). Pitfalls: macOS schemes must be in `tauri.conf` + app in /Applications to test; Linux AppImage moves invalidate registration; Snap/Flatpak need explicit D-Bus plugs; custom-scheme navigation may need a user gesture (UNVERIFIED, reported in Tauri discussions 2025).

**Device Grant (RFC 8628, Aug 2019) as fallback** — `POST /device_authorization` → user code + verification URI → poll `urn:ietf:params:oauth:grant-type:device_code` handling `authorization_pending/slow_down/access_denied/expired_token`. Wins headless/SSH/VM/no-local-browser; loses on workstation (slower, phishing surface: attacker tricks victim into entering a code — must show app/org name + explicit confirm, short code lifetime, rate-limit). Current consensus (WorkOS, 2026-05-08): **ship both, default PKCE, `--device` fallback**; AWS CLI v2.22 flipped its default the same way. Sources: https://www.rfc-editor.org/info/rfc8628/; https://workos.com/blog/pkce-vs-device-flow-cli-auth (2026-05-08). VERIFIED.

**Refresh rotation + revocation:** RFC 9700 §4.14 — new refresh token per use, invalidate lineage, replay of a dead token = breach signal = revoke whole family; also revoke on password-change/logout. GitHub's current behavior matches (8h access, 6mo sliding refresh, `bad_refresh_token` → re-run flow). Desktop: store refresh in OS keychain, revoke via RFC 7009 + local delete, `invalid_grant` → wipe and re-login. Sources: GitHub authorizing-OAuth-apps docs (fetched 2026-10-16); https://better-auth.com/docs/plugins/oauth-provider (2026). VERIFIED.

**Real implementations:** `gh`/`cli/oauth` (device-first + loopback fallback; per-device token lineage MISSING — cli/cli#11420 — lesson: issue per-device clients); VS Code (loopback + PKCE, `vscode://` deep links; remote-SSH needed a relay extension — lesson for any remote story); Docker `mcp-gateway/pkg/oauth` v0.43.1 (explicit `127.0.0.1`, fixed-port override, DPoP-ready, copy-paste URL fallback — closest to our shape). VERIFIED via repos/docs linked in §8.

**Adding an OAuth2/OIDC server to our Next.js portal (Auth.js is client-only — no `/authorize`, `/token`, JWKS exist; VERIFIED https://authjs.dev/guides/configuring-oauth-providers):**

Requires own login/consent UI + adapters. https://github.com/panva/node-oidc-provider |

## b) Secure token storage in Tauri

**`keyring` 4.2.0 (2026-08-29; `keyring-core` 1.0.1, 2026-10-13) — recommended default.** Facade split: depend on `keyring-core` + only the stores you need. Backends VERIFIED current: macOS `apple-native-keyring-store` 1.0.2 (Keychain + Protected Data), Windows `windows-native-keyring-store` 1.1.0 (Credential Manager, per-entry persistence), Linux `zbus/dbus-secret-service-keyring-store` 1.0.1 (Secret Service over D-Bus) + `linux-keyutils` 1.0.0 + file-backed `db-keystore` fallback. Sources: crates.io registry API; https://docs.rs/keyring/ (4.2.0); https://github.com/open-source-cooperative/keyring-rs (771★). VERIFIED.

**Known limitations (all primary-sourced):** headless Linux = problematic (needs unlocked daemon; WSL no default collection; KWallet UTF-8-only — base64 secrets); Flatpak/Snap can't reach session-bus Secret Service (sanctioned path is `oo7-portal`); concurrent same-entry access does NOT reliably serialize (mutex it); duplicate `service+user` items → `Error::Ambiguous`; error enum (`NoStorageAccess`, `PlatformFailure`, `NoEntry`, `Ambiguous`, …) must all be handled. UX mapping: `NoEntry` = logged-out state (silent re-login); `NoStorageAccess`/`PlatformFailure` = retry once → unlock guidance → re-login; logout = `delete_credential` + zeroize + confirm.

**Tauri Stronghold: maintained, not deprecated.** `tauri-plugin-stronghold` 2.4.0 (2026-09-26), 3.0.0-alpha.3 (2026-10-14). A secondary claim that Stronghold is "deprecated/removed in v3" (mailkite docs + Reddit) is contradicted by the registry (alphas shipping Sep–Oct 2026) — **trust the registry; deprecation rumor tagged UNVERIFIED/false.** Stronghold stores an encrypted snapshot (`vault.hold`) unlocked by an app-managed password (secret-zero problem), has documented perf issues (snapshot load slowness; official page prescribes scrypt opt-level workaround), snapshot corruption = total loss. Use only if Linux-headless must work without a keyring daemon. Reject: `tauri-plugin-store` (plaintext JSON), `windows-dpapi` (niche), raw `secret-service`/`oo7` (plumbing; keyring already wraps them). Sources: crates.io; https://v2.tauri.app/plugin/stronghold/ (Dec 2025). VERIFIED, except snapshot cipher suite (AES-256-GCM vs XChaCha20-Poly1305) — UNVERIFIED, confirm in engine docs before repeating.

**Tauri v2 hardening (all docs current, 2025–2026):** deny-by-default capabilities + per-command `allow/deny` and argument scopes (https://v2.tauri.app/security/capabilities/ Sep 2026; /permissions Jul 2026); set `app.security.csp`, never ship `"csp": null`; `assetProtocol` deny-by-default with `requireLiteralLeadingDot` Unix gotcha; webview = untrusted, IPC bridge = choke point. **Credential consequence: never expose get/set/delete-token `#[tauri::command]`s to the webview** — do token I/O in Rust event handlers/menu/setup code. VERIFIED.

## d) Prior art: "login with portal, then configure CLI"

Fragile: only Claude hot-reloads (Codex/OpenCode need restart — UX trap), `cc-switch.db` lock with two instances, preset ecosystem dominated by third-party relays (supply-chain trust), OAuth re-login loops. Sources: repo + ofox.ai setup guide (verified v3.20.1, 2026-08-28). VERIFIED where stated.

## e) Gateway quota patterns

**LiteLLM (rolling docs, fetched 2026-10-16; my pin v1.103.1):** `POST /key/generate` budgets (`max_budget`, `budget_duration`, `budget_limits[]`, `tpm/rpm_limit`, `model_max_budget`, `soft_budget`, `duration`); team-key rule — **team budget wins, personal budget ignored**; budgets REQUIRE a database (else silently unenforced). Spend endpoints: `/key/info`, `/user|team|customer/info`, `/spend/*` (admin or `permissions.get_spend_routes`). Error semantics (error_reference, 2026 examples — newest canonical; older 400/422/401 budget shapes treated as legacy): budget-exceeded → **429 `type: budget_exceeded`** (message embeds figures), rate/concurrency → **429 `throttling_error` + `retry-after`/`rate_limit_type`/`reset_at`**, allowlist → **403 `key_model_access_denied`**, unknown/expired → **401**. **429 + `retry-after`/`rate_limit_type`/`reset_at` = gateway; 429 without = provider.**

**Headers (VERIFIED live on v1.103.1, 2026-10-16, my probe: minted $1 key → non-stream chat → `/key/info` → deleted key):** success carries `x-litellm-key-spend`, `x-litellm-key-max-budget`, `x-litellm-response-cost*` (components, **non-streaming only**), `x-litellm-{call-id,model-group,model-id,response-duration-ms,…}`; **no `x-ratelimit-*` on that call because the key had no rpm/tpm limits** (docs: rate headers only when key has limits; `x-litellm-key-remaining-{requests,tokens}-{model}` shape documented — presence on our build UNVERIFIED). **No budget-remaining/reset headers exist** (docs + source: `parallel_request_limiter.py` success hook writes rate headers only; error-reference: rate headers are success-only). Budget 429 carries **no `Retry-After`** (rate/cooldown 429s do). Mid-stream failures arrive as SSE `data:{"error":…}` under HTTP 200 — clients must scan chunks; `stream_options:{include_usage:true}` recovers usage.
⚠️ Probe note: `GET /key/info?key=<plaintext>` with master key returned all-null fields in my probe while spend demonstrably accrued — use the portal's existing client shape (proven by verify-metering), not the query-param form, until re-tested. Also: `GET /v1/models` with a tenant key returns **only that key's allowlist** (`['fast']` for a fast-only key) — entitlement filtering works and the desktop MUST treat it as the entitled set. And `x-litellm-model-name` leaks the upstream model id in response headers — never surface raw headers in UI (alias invariant).

**Peers (all fetched 2026-10-16):** OpenRouter — no success headers; platform 429s carry `X-RateLimit-*`; out-of-credit is **402** with machine-readable `metadata.limit_source` (`in_flight_budget` = retryable vs `credits`/`key_limit` = act) — cleanest design found: **branch on a code, not on hint text**; `GET /api/v1/key` → `effective_budget{remaining_usd,resets_at}` (pre-flight checks endorsed). OpenAI — `x-ratelimit-*` success headers, `Retry-After` on transient 429/503 only, `insufficient_quota` = do-not-retry, soft (alert) vs hard (block) spend limits. Anthropic — `anthropic-ratelimit-*-{limit,remaining,reset}` (tokens = most-restrictive), spend-cap 429 NEVER carries retry-after (`details.error_code=enforced_spend_limit_reached`), 529 overloaded, workspace 400-vs-429 nuance. Together — 429/503 + backoff only, nothing else documented.

**Client rules (convergent):** retry 429-with-`Retry-After` (wait header + jitter, capped); NEVER retry budget/quota 429 without it, 402 (except OpenRouter transient), 403, 401 (one silent refresh only if you own OAuth); retry 5xx/408 with exp backoff + full jitter; mid-stream SSE error = fail the turn, never auto-replay consumed output; fail the turn fast, keep the agent loop alive, surface structured errors (status + type + reset + call/request id). **Soft/hard UX:** soft = non-blocking banner with remaining % + manage link; hard = blocking state with what-hit + figures + exact reset + who-can-raise. Cache display snapshot (`spend/limit/resets_at/fetched_at`, render age; stale > one window = unknown, not zero); **never gate requests client-side on cache**; any 401/402/403/429 busts the cache and re-fetches truth.

## f) Token/key/proxy designs with precedent + pitfalls

**Precedents.** (A) write-into-native-config: `gh --with-token` → `hosts.yml`, `git-credential-store` (owner-only perms, no locking), AWS `credential_process` (stdout JSON + `Expiration`, re-run before expiry — the rotation pattern to copy), 1Password `op run/inject` (env-only for subprocess lifetime; warns same-user env readable), Aider (`--flag`/env/`.env`/`.aider.conf.yml`). (B) loopback proxy: RFC 8252 §7.3 bind pattern; `gcloud`/`aws sso login` ephemeral-127.0.0.1 + PKCE (2025–2026); Cloud SQL Auth Proxy (app→`localhost:port` plaintext, proxy adds IAM+TLS upstream — sanctioned same-host pattern); LiteLLM `pass_through_endpoints` + `forward_client_headers` (proxy downstream-auth, inject upstream key; `GOOGLE_GEMINI_BASE_URL=http://localhost:4000` Gemini-CLI tutorial, needs v1.73.3+); Claude Code gateway docs (`ANTHROPIC_BASE_URL` + `AUTH_TOKEN`→Bearer/`API_KEY`→x-api-key, `apiKeyHelper` 5-min cache); Codex `auth.command` (`refresh_interval_ms` default 300000, `0` = refresh-on-retry-only); Gemini CLI `GOOGLE_GEMINI_BASE_URL`. (C) hybrids: 1Password env+file together; LiteLLM strip-proxy-key/forward-user-key; per-provider static-vs-helper split in Claude/Codex. Sources: vendor docs linked per claim, all fetched 2026-10-16 (AWS v1 `credential_process` page carries a maintenance banner — pattern trusted, exact JSON re-verify against v2 `sdkref` at implementation).

**Pitfalls for our traffic.** Streaming: proxy MUST stream, never buffer — axum `Sse: Stream<Event>`, hyper bodies stream (docs.rs axum 0.8.9, 2026-09-22); traps: `tower-http` compression buffering SSE (axum #2891), missing flush batching realtime into lumps; mitigations `proxy_buffering off; gzip off; X-Accel-Buffering: no`, `proxy_read_timeout 1h`, LiteLLM `pass_through encoding: no-op`. Timeouts: TWO layers must both be raised/disabled — Claude `API_TIMEOUT_MS=600000` + 5-min body-idle watchdog (`API_FORCE_IDLE_TIMEOUT`), Codex `stream_idle_timeout_ms=300000`, LiteLLM `pass_through_request_timeout=600s`; axum `TimeoutLayer` must exclude stream routes (use `Sse::keep_alive`). Rotation mid-session: in-flight SSE CANNOT have headers swapped — stream dies and must retry from checkpoint; proxy wins BETWEEN requests (proactive refresh, no child restart) while file-design needs CLI re-read/restart. Loopback latency negligible vs LLM TTFT (~0.03–0.3 ms; old benchmarks — direction trusted, numbers UNVERIFIED at our payloads; UDS unusable — CLIs speak `http://` only). TLS: plain HTTP on `127.0.0.1` acceptable (RFC 8252 §8.3, Cloud-SQL model); bind `127.0.0.1` never `0.0.0.0`; per-child dummy key; OS user separation is the boundary. Large payloads/WS: forward chunked + upgrade bytes unmodified, disable body limits on inference routes, forward `anthropic-beta`/`x-api-key`/`Authorization` verbatim.

**Refresh behavior per CLI (2026 docs):** Claude — `apiKeyHelper` re-run after TTL (5 min default) else static env at startup; Codex — `auth.command` proactive `refresh_interval_ms`, `0` = refresh-on-auth-retry; file-edit pickup interval UNKNOWN (assume restart); Gemini CLI — cached session may IGNORE `BASE_URL` in some builds (#15430, UNKNOWN on target version); Aider — startup-read, no in-run refresh documented.

## g) Tauri updater + per-OS signing

**Custom endpoint (Tauri v2 docs, updated Nov 2025):** static `latest.json` `{version, notes?, pub_date? (RFC3339), platforms:{<os>-<arch>[-<bundle_type>]:{url,signature}}}` — every listed entry must be complete; dynamic server may use `{{current_version}}/{{target}}/{{arch}}/{{bundle_type}}` and answers `204` (no update) or `200` + object; HTTPS required in prod; client tries next URL only on non-2xx. Bundle-specific targets (`linux-x86_64-appimage` vs `-deb`): PR #2624 — **pin `@tauri-apps/plugin-updater` ≥ that change and test the deb path** (older guides saying "Linux updater = AppImage only" are STALE; `.deb` support is new). No built-in staged rollouts (static = all-or-nothing; staging needs dynamic server or CrabNebula Cloud). Downgrade prevention default (`version > current`); rollback = server + `version_comparator` override (Windows MSI also `allowDowngrades`). **Keys: `tauri signer generate` (Ed25519/minisign-compatible); `pubkey` embedded verbatim; `TAURI_SIGNING_PRIVATE_KEY[_PASSWORD]` in CI (`.env` files do NOT work); rotation = manual (ship N with old key + new pubkey, N+1 on new key; single-key only — issue #7585); lost key = forced manual reinstall. Broken-key advisory: CLI 2.9.3–2.10.0 empty-password keys unusable — regenerate.**
